# r11: recorded-input 60Hz performance checkpoint

## Decision and scope

Close the current optimization round for this recorded-input workload. Retain
DWPose-m same-frame batch-2 with detector=CoreML ALL, pose=CoreML ALL, explicitly
allowed ORT CPU partitions, one pose owner, OpenCV normalization and ready-only
handoff as the research candidate for the next live integration slice.

This is an engineering milestone decision, NOT a predeclared latency-SLA pass,
proof that no further optimization is possible, live-camera 60FPS approval, or
promotion to the application's live default. The r11 run changes the host release
schedule, not the inference algorithm. No further rerun of this same clip is
required merely to close this round.

This checkpoint changes documentation only. It adds no model, capture, inference,
preview, transport or default-setting change. It does not launch a new benchmark.

## Limits that remain open

1. Fixed60 is a schedule, not perfectly regular actual camera admission. Peak
   detector release lateness is 48.23121ms / 45.78458ms. The JSON field
   `configured_and_observed_release_rate_60hz` checks configured/scheduled rate;
   it must not be read as proof of punctual hardware capture.
2. Output is not locked to one new result every 16.667ms: fixed60 validation
   interval p95 is 19.57792ms / 19.24954ms and max is 44.81517ms / 45.71158ms.
   Interval-budget exceedances are not dropped-frame counts.
3. Each run contains 5,991 one-slot, 130 two-slot, 320 zero-slot and one three-slot
   frames. Only 2.0335% contain multiple detector slots. These are detections,
   not verified performers. Sustained two- or three-performer 60Hz is unverified.
   Two-slot pose stage means are 17.45828ms / 16.91149ms, already above a 60Hz
   period; do not extrapolate the mostly-single-person result to studio capacity.
4. One recording and one reported macOS runtime do not establish long-session
   thermal/memory stability, M1 performance, Windows performance, live capture,
   GUI/preview or transmission/display latency. Physical GPU/ANE dispatch remains
   unverified. COCO-WholeBody133 2D is not 3D capture, actor association, ARKit
   blendshapes, skeleton solving or retargeting. Accuracy and commercial release
   clearance remain false/unreviewed.

## Next boundary

The next useful slice is an explicitly selected live camera path using this
candidate, with real capture timestamps, bounded admission, observable shutdown,
preview/output costs and displayed result age. Define that slice and its latency,
frame-loss and duration requirements before implementation or evaluation. Do not
keep changing the replay goalposts or claim this checkpoint implements that path.
Any future runtime change should be compared against this recorded-input evidence
as well as the live requirements; preserve existing user-owned changes and logs.
